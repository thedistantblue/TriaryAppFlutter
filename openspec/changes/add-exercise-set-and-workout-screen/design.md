# Design

## Context

См. `proposal.md` — Why. Ниже только то, что определяет подход.

- Проект — melos-воркспейс: приложение (`lib/`) + 4 библиотечных пакета (`packages/entity`, `storage_api`, `storage_local_api`, `storage_mock_api`). Стек: provider (DI), flutter_bloc 9, drift (локальная SQLite), json_serializable, l10n через ARB (ru/en), `intl: any`.
- Существующая модель: `PowerTraining {id, name, description}` — неизменяемая сущность с `copyWith`, id генерирует репозиторий (в сущности `''` как сериализуемый сентинел), `props` для equatable. Хранение — JSON-blob: таблица `power_training_table` (PK `id` + колонка `data` через `TypeConverter.json`).
- Миграции уже применялись: `schemaVersion = 2`, в `onUpgrade` есть шаг `from < 2` (пересоздание таблицы ради PK). Паттерн колонок-дублёров уже существует: `id` лежит и как PK-колонка, и внутри JSON.
- Экранов тренировки ещё нет: `pt_details.dart` (борд 04) показывает три тайла и ничего больше; блок `PowerTrainingBloc` привязан к `TabsScreen` и в пушнутый маршрут не попадает.
- Дизайн — авторитетный источник (Penpot: `04 Training details`, `09–13 Workout`). Значения цветов/размеров ниже сняты с бордов и не подлежат «улучшению».
- Dart/Flutter в песочнице нет: codegen (`build_runner` через melos) и `flutter analyze` запускает пользователь локально.

## Goals / Non-Goals

**Goals:**

- Описать набор упражнений как сущность и связать его с тренировкой на уровне базы (миграция без потери данных).
- Свести пять бордов (09–13) к одному экрану с явно вычислимыми состояниями.
- Дать следующий шаг (создание/выбор набора) точку подключения: репозиторий наборов + метод простановки ссылки.

**Non-Goals:**

- UI создания/редактирования наборов и экрана выбора набора.
- Большой AppBar и описание на борду 04 (только кнопка).
- Логика запуска тренировки, история тренировок, тесты.

## Decisions

### 1. Форма сущностей: `ExerciseSet` и `Exercise` в `packages/entity`

```dart
class ExerciseSet with Equatable {
  ExerciseSet({this.id = '', required this.name, this.exercises = const <Exercise>[]});
  final String id;      // '' = черновик, id выдаёт репозиторий (как у PowerTraining)
  final String name;
  final List<Exercise> exercises;
}

class Exercise with Equatable {
  Exercise({required this.name, required this.sets, required this.reps});
  final String name;
  final int sets;   // подходы
  final int reps;   // повторы
}
```

Плюрализация и формат «3 × 10» — не в сущности, а в UI/локализации.

Альтернатива — хранить упражнения списком прямо в `PowerTraining` — отклонена: набор переиспользуется несколькими тренировками, и под будущее создание наборов нужен собственный id.

### 2. Связь: поле `setId` в сущности + реальная колонка в базе

- `PowerTraining` получает `final String setId` с дефолтом `''` (сентинел «набор не выбран», без `String?` и без `!` в UI — тот же приём, что с `id`).
- В `power_training_table` добавляется nullable-колонка `set_id`; в базу пишется `setId.isEmpty ? null : setId`.
- Новая таблица `exercise_set_table` (PK `id` + `data` через тот же JSON-конвертер) и новый репозиторий `ExerciseSetRepository`.
- Простановка ссылки после создания тренировки — новый метод `update(PowerTraining training)` в `BasePowerTrainingRepository` (+ drift-реализация + mock). Вызовов у него в этой итерации нет: это API, которым воспользуется будущая фича выбора набора (`training.copyWith(setId: ...)`).

Почему колонка, а не только JSON: связь должна быть видна самой базе (в том числе для будущих запросов «какие тренировки используют этот набор»), а `BaseRepository` не умеет читать поля из blob. Дубль `setId` в JSON и в колонке — осознанная цена, ровно как с `id`; единственная точка записи — `create()`/`update()` репозитория, данные в колонку берутся из сущности.

### 3. Миграция drift: schemaVersion 2 → 3

```dart
onUpgrade: (m, from, to) async {
  if (from < 2) { /* существующий шаг: пересборка таблицы ради PK */ }
  if (from < 3) {
    await m.addColumn(powerTrainingTable, powerTrainingTable.setId); // nullable → безопасно
    await m.createTable(exerciseSetTable);
  }
}
```

Существующие тренировки получают `set_id = NULL`, то есть состояние «набор не выбран» (борд 13) — данные не теряются. `onCreate` остаётся `createAll()`. Пересоздавать таблицы не нужно: SQLite умеет `ALTER TABLE ADD COLUMN` для nullable-колонки.

### 4. Пять бордов = один экран с вычислимым состоянием

| Борд | Условие | Что видно |
|---|---|---|
| 13 | набор не выбран (`setId` пуст или набор не найден) | выделенный виджет выбора набора, нулевая сводка, «Начать»/«Редактировать» disabled |
| 09 | набор выбран, развёрнут, упражнений ≤ 3 | имя набора + все упражнения + сводка |
| 11 | набор выбран, развёрнут, упражнений > 3 | 3 упражнения + футер «и ещё N упражнений» + сводка по всему набору |
| 10 | набор выбран, свёрнут | только имя набора, сводка поднята под карточку |
| 12 | из 09/11 открыта шторка | полный список набора поверх экрана |

Состояние — данные блока (`training`, `set`) плюс два UI-флага: `isExpanded` (по умолчанию `true`) и факт открытой шторки. Шторка императивна (`showModalBottomSheet`), в состоянии блока не хранится. Лимит строк — константа `kSetPreviewLimit = 3`, N = `exercises.length - 3`.

### 5. `WorkoutBloc` вместо `FutureBuilder`, `PreferredSize` вместо `AppBar.large`

- Новый маршрут `/workout` с `arguments: PowerTraining`; `WorkoutBloc` создаётся на маршруте (`BlocProvider`), потому что `PowerTrainingBloc` живёт внутри `TabsScreen` и в пушнутом маршруте недоступен. События: `WorkoutStarted(training)`, `SetExpansionToggled()`. Загрузка набора — `ExerciseSetRepository.findById(training.setId)`; отсутствие набора — не ошибка, а состояние 13.
- Верх экрана — `PreferredSize` высотой 136 с фоном `#1C2129` (стрелка назад 24 в (16,16), имя 28/600 на y=50, описание 14 `#9AA3AE` на y=92, разделитель 1px `#3A424E` на 136). `AppBar.large` даёт другую геометрию и не попадает в макет.

### 6. Значения из дизайна (использовать как есть)

- Карточка набора: 312 ширина, радиус 16, фон `#1C2129`; header 64px (имя 20/600 `#E5E9EF`, chevron 24 справа, повёрнут на 90° в развёрнутом состоянии), разделитель `#3A424E`, строки упражнений по 48 (имя 15/400 `#E5E9EF`, повторы 14/400 `#9AA3AE` справа), футерная строка 48 с chevron_right.
- Сводка: карточка 312×40, радиус 12, `#1C2129`, содержимое по центру; числа 14/600, подписи 13/400, разделители «·» `#3A424E`. Цвет чисел: `#48CAA0` когда набор выбран, `#9AA3AE` в состоянии 13. Время — «~N мин».
- Кнопки: высота 48, радиус 24, лейбл 15/600. «Предыдущие тренировки» — `secondary` `#7CC7E8` / текст `#0A1A24`; «Редактировать» — `tertiary` `#A78BFA` / текст `#1B1140`; «Начать» — `primary` `#48CAA0` / текст `#0A1F18`.
- Тема приложения (`lib/main.dart`) дополняется `tertiary: 0xFFA78BFA`, `onTertiary: 0xFF1B1140` — этих ролей в текущей `ColorScheme` нет.
- Disabled-состояние (борд 13): контейнер `#2C3039`, лейбл `#72767E`. Дефолты M3 дают другое (`onSurface` 12%/38% от `#1C2129`), это проверено расчётом, поэтому цвета disabled задаются явно в стиле кнопок.
- Виджет выбора набора в состоянии 13: фон `#1C3436`, обводка 1px `#48CAA0`, лейбл «Выбрать набор упражнений» 15/600 `#48CAA0`, chevron primary.
- Виджет набора рендерится одним виджетом `SetCard` (высота вычисляется: 64 + разделители + 48·строки + 48·футер) — без `ExpansionTile`, потому что нужен футер внутри карточки и точные размеры строк.

### 7. Сводка: расчёт и локализация

- Число упражнений = `set.exercises.length`; подходы = сумма `exercise.sets`; время = `sets == 0 ? 0 : max(10, (sets * 4 / 10).round() * 10)` — сверено с макетом: 9 подходов → ~40, 21 → ~80.
- Сводка рисуется одним `Text.rich` (числа и подписи — разные стили, разделители — третий), содержимое центрируется по карточке.
- Плюрализация — ICU-плюралы в ARB (`one/few/many/other`), потому что дизайн требует «21 подход», «7 упражнений», «9 подходов», «и ещё 4 упражнения». Новые ключи: `startTraining`, `changeSet`, `chooseSet`, `start`, `edit`, `previousTrainings`, `exercisesCount`, `setsCount`, `durationApprox`, `moreExercises`. Подзаголовок шторки собирается в коде как `exercisesCount · setsCount` (в макете у шторки времени нет, в отличие от сводки), повторы — как `'$sets × $reps'`.

### 8. Кнопка на борду 04

`Scaffold.body` становится `Column`: `Expanded(ListView(...))` + нижний блок `SafeArea(Padding(horizontal: 16, bottom: 16, child: FilledButton(height 48, radius 24, primary)))` с `pushNamed('/workout', arguments: training)`. Не `bottomNavigationBar` — так кнопка не перекрывает список и повторяет макет (кнопка на y=716, отступ 16).

## Risks / Trade-offs

- [Дубль `setId` в JSON и в колонке может разойтись] → единственная точка записи — `create()`/`update()` репозитория, значение всегда берётся из сущности; сущность остаётся source of truth для приложения.
- [`setId` указывает на удалённый набор] → трактуется как «набор не выбран» (сценарий в spec `exercise-sets`), отдельной чистки ссылок не делаем.
- [`update()` в этой итерации никем не вызывается и на устройстве не проверяется] → принято сознательно: это точка подключения будущей фичи выбора набора; API минимальный (обновление сущности целиком), чтобы не угадывать лишнего.
- [Состояния 09–12 нельзя увидеть на устройстве: демо-данных нет, а создания наборов ещё нет] → следствие решения «не сеять данные»; проверяемы на живом приложении только борд 04 и состояние 13, остальные — по `flutter analyze` и последующему появлению набора.
- [Локальная БД у пользователя уже с данными] → миграция `from < 3` только добавляет nullable-колонку и таблицу; потери данных быть не может, но при первом запуске новой версии миграция выполнится до первого чтения — проверяется на устройстве.
- [Сгенерированный код (`*.g.dart`) в песочнице не перегенерировать] → Dart в песочнице нет, поэтому `.g.dart` правится вручную по детерминированному виду (для дефолтных полей json_serializable даёт `json['setId'] as String? ?? ''`), а пользователь прогоняет `dart run melos run codegen` и убеждается, что диффа нет.
- [Нет данных для перехода на борд 04] → если на устройстве ещё нет ни одной тренировки, ручная проверка кнопки упрётся в пустой список: проверяем на существующей тренировке либо создаём её через уже работающий диалог, и сообщаем результат отдельно.
- [Расхождение с макетом по мелочам (высоты, отступы)] → значения выписаны из бордов и перечислены в этом документе; спорит с ними только макет.
