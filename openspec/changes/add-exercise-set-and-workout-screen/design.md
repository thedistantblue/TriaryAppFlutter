# Design

## Context

См. `proposal.md` — Why. Ниже только то, что определяет подход.

- Проект — melos-воркспейс: приложение (`lib/`) + 4 библиотечных пакета (`packages/entity`, `storage_api`, `storage_local_api`, `storage_mock_api`). Стек: provider (DI), flutter_bloc 9, drift (локальная SQLite), json_serializable, l10n через ARB (ru/en), `intl: any`.
- Существующая модель: `PowerTraining {id, name, description}` — неизменяемая сущность с `copyWith`, id генерирует репозиторий (в сущности `''` как сериализуемый сентинел), `props` для equatable. Хранение — JSON-blob: таблица `power_training_table` (PK `id` + колонка `data` через `TypeConverter.json`).
- Сейчас в `database.dart` есть `schemaVersion = 2` и шаг `onUpgrade` `from < 2` (пересоздание таблицы ради PK). По решению из proposal миграции удаляются целиком — приложение в разработке, совместимость с прежними сборками не поддерживаем.
- Паттерн колонок-дублёров уже существует: `id` лежит и как PK-колонка, и внутри JSON.
- Экранов тренировки ещё нет: `pt_details.dart` (борд 04) показывает три тайла и ничего больше; блок `PowerTrainingBloc` привязан к `TabsScreen` и в пушнутый маршрут не попадает.
- Дизайн — авторитетный источник (Penpot: `04 Training details`, `09–13 Workout`). Значения цветов/размеров ниже сняты с бордов и не подлежат «улучшению».
- Dart/Flutter в песочнице нет: codegen (`build_runner` через melos) и `flutter analyze` запускает пользователь локально.

## Goals / Non-Goals

**Goals:**

- Описать упражнение и набор как самостоятельные сущности, связать их многие-ко-многим и привязать набор к тренировке.
- Держать модель без миграций: одна актуальная схема, создаваемая с нуля.
- Свести пять бордов (09–13) к одному экрану с явно вычислимыми состояниями.
- Дать следующему шагу (создание упражнений и наборов, выбор набора) точку подключения: репозитории и метод простановки ссылки.

**Non-Goals:**

- UI создания/редактирования упражнений и наборов, экрана выбора набора.
- Каскадное удаление, чистка «осиротевших» записей, внешние ключи.
- Большой AppBar и описание на борду 04 (только кнопка).
- Логика запуска тренировки, история тренировок, тесты.

## Decisions

### 1. Сущности: `Exercise` и `ExerciseSet` в `packages/entity`

```dart
class Exercise with Equatable {
  Exercise({this.id = '', required this.name, required this.sets, required this.reps});
  final String id;   // '' = черновик, id выдаёт репозиторий (как у PowerTraining)
  final String name;
  final int sets;    // подходы
  final int reps;    // повторы
}

class ExerciseSet with Equatable {
  ExerciseSet({this.id = '', required this.name, this.exerciseIds = const <String>[]});
  final String id;
  final String name;
  final List<String> exerciseIds;  // порядок в списке = порядок показа
}
```

Подходы и повторы принадлежат упражнению (решение пользователя): «Жим штанги лёжа 3×10» — одна запись справочника, которую переиспользуют наборы; связка хранит только порядок. Цена: одно и то же движение с разными подходами — две записи справочника; это принимается, редактирование справочника — будущая фича.

### 2. Три таблицы и линк-таблица с порядком

- `exercise_table` (PK `id` + `data` через JSON-конвертер) — записи справочника.
- `exercise_set_table` (PK `id` + `data`) — наборы; `exerciseIds` едет внутри JSON.
- `exercise_set_link_table` — связка: `set_id` (text), `exercise_id` (text), `position` (int), PK `{setId, exerciseId}`.

Почему линк-таблица, а не только список id в JSON: связь многие-ко-многим должна быть видна самой базе («в каких наборах встречается упражнение»), а `BaseRepository` не читает поля из blob. Почему `position`: порядок показа должен существовать и на уровне базы, иначе линк-таблица не самодостаточна. Список `exerciseIds` в JSON — источник порядка для приложения, колонка `position` пишется тем же порядком (0..n-1). Дубль осознанный, как с `id`/`set_id`; единственная точка записи — `ExerciseSetRepository.create()` в одной транзакции.

Внешние ключи и `references` не ставим: в SQLite их надо включать прагмой, а потоков удаления пока нет. Целостность — забота репозитория, «висячие» идентификаторы просто пропускаются при чтении.

### 3. Схема без миграций

```dart
@DriftDatabase(tables: [PowerTrainingTable, ExerciseTable, ExerciseSetTable, ExerciseSetLinkTable])
class AppDatabase extends _$AppDatabase {
  @override
  int get schemaVersion => 1;
  // MigrationStrategy удаляется целиком; drift использует дефолт onCreate: createAll()
}
```

Существующий `onUpgrade` (включая шаг `from < 2` и `customStatement`-пересборку) убирается. Следствия, принятые сознательно: база прежних сборок новой схемой не открывается (в debug drift сообщит о несоответствии схемы) — на устройстве приложение переустанавливается или очищаются его данные. Новая колонка `set_id` и три таблицы появляются сразу в `createAll()`, поэтому `addColumn`/`createTable` в апгрейде не нужны.

### 4. Ссылка тренировки на набор: поле + колонка

- `PowerTraining` получает `final String setId` с дефолтом `''` (сентинел «набор не выбран», без `String?` и без `!` в UI).
- В `power_training_table` — nullable-колонка `set_id`; в базу пишется `setId.isEmpty ? null : setId`.
- Простановка ссылки — новый метод `update(PowerTraining training)` в `BasePowerTrainingRepository` (+ drift-реализация + mock). Вызовов в этой итерации нет: это API для будущей фичи выбора набора (`training.copyWith(setId: ...)`).

### 5. Чтение данных экрана: набор → список id → упражнения

`WorkoutBloc` делает два запроса: `ExerciseSetRepository.findById(training.setId)`, затем `ExerciseRepository.findAllById(set.exerciseIds)`. Порядок строк берётся из `set.exerciseIds`, а не из порядка строк базы: локальная реализация `findAllById` собирает результат, проходя по переданному списку id и пропуская отсутствующие (SQL `IN` порядок не гарантирует, а `PowerTrainingRepository.findAllById` его и не восстанавливает — для нового репозитория делаем правильно). Пустой `setId`, набор, которого нет, и пустой список упражнений — не ошибки, а состояния борда 13 / пустого набора.

### 6. Пять бордов = один экран с вычислимым состоянием

| Борд | Условие | Что видно |
|---|---|---|
| 13 | набор не выбран (`setId` пуст или набор не найден) | выделенный виджет выбора набора, нулевая сводка, «Начать»/«Редактировать» disabled |
| 09 | набор выбран, развёрнут, упражнений ≤ 3 | имя набора + все упражнения + сводка |
| 11 | набор выбран, развёрнут, упражнений > 3 | 3 упражнения + футер «и ещё N упражнений» + сводка по всему набору |
| 10 | набор выбран, свёрнут | только имя набора, сводка поднята под карточку |
| 12 | из 09/11 открыта шторка | полный список набора поверх экрана |

Состояние — данные блока (`training`, `set`, `exercises`) плюс `isExpanded` (по умолчанию `true`); факт открытой шторки императивен (`showModalBottomSheet`) и в состоянии блока не хранится. Лимит строк — константа `kSetPreviewLimit = 3`, N = `exercises.length - 3`.

### 7. `WorkoutBloc` вместо `FutureBuilder`, `PreferredSize` вместо `AppBar.large`

- Новый маршрут `/workout` с `arguments: PowerTraining`; `WorkoutBloc` создаётся на маршруте (`BlocProvider`), потому что `PowerTrainingBloc` живёт внутри `TabsScreen` и в пушнутом маршруте недоступен. События: `WorkoutStarted(training)`, `SetExpansionToggled()`.
- Верх экрана — `PreferredSize` высотой 136 с фоном `#1C2129` (стрелка назад 24 в (16,16), имя 28/600 на y=50, описание 14 `#9AA3AE` на y=92, разделитель 1px `#3A424E` на 136). `AppBar.large` даёт другую геометрию и не попадает в макет.

### 8. Значения из дизайна (использовать как есть)

- Карточка набора: 312 ширина, радиус 16, фон `#1C2129`; header 64px (имя 20/600 `#E5E9EF`, chevron 24 справа, повёрнут на 90° в развёрнутом состоянии), разделитель `#3A424E`, строки упражнений по 48 (имя 15/400 `#E5E9EF`, повторы 14/400 `#9AA3AE` справа), футерная строка 48 с chevron_right.
- Сводка: карточка 312×40, радиус 12, `#1C2129`, содержимое по центру; числа 14/600, подписи 13/400, разделители «·» `#3A424E`. Цвет чисел: `#48CAA0` когда набор выбран, `#9AA3AE` в состоянии 13. Время — «~N мин».
- Кнопки: высота 48, радиус 24, лейбл 15/600. «Предыдущие тренировки» — `secondary` `#7CC7E8` / текст `#0A1A24`; «Редактировать» — `tertiary` `#A78BFA` / текст `#1B1140`; «Начать» — `primary` `#48CAA0` / текст `#0A1F18`.
- Тема приложения (`lib/main.dart`) дополняется `tertiary: 0xFFA78BFA`, `onTertiary: 0xFF1B1140` — этих ролей в текущей `ColorScheme` нет.
- Disabled-состояние (борд 13): контейнер `#2C3039`, лейбл `#72767E`. Дефолты M3 дают другое (`onSurface` 12%/38% от `#1C2129`), это проверено расчётом, поэтому цвета disabled задаются явно в стиле кнопок.
- Виджет выбора набора в состоянии 13: фон `#1C3436`, обводка 1px `#48CAA0`, лейбл «Выбрать набор упражнений» 15/600 `#48CAA0`, chevron primary.
- Набор рендерится одним виджетом `SetCard` (высота вычисляется: 64 + разделители + 48·строки + 48·футер) — без `ExpansionTile`, потому что нужен футер внутри карточки и точные размеры строк.

### 9. Сводка: расчёт и локализация

- Число упражнений = `exercises.length`; подходы = сумма `exercise.sets`; время = `sets == 0 ? 0 : max(10, (sets * 4 / 10).round() * 10)` — сверено с макетом: 9 подходов → ~40, 21 → ~80.
- Сводка рисуется одним `Text.rich` (числа и подписи — разные стили, разделители — третий), содержимое центрируется по карточке.
- Плюрализация — ICU-плюралы в ARB (`one/few/many/other`), потому что дизайн требует «21 подход», «7 упражнений», «9 подходов», «и ещё 4 упражнения». Новые ключи: `startTraining`, `changeSet`, `chooseSet`, `start`, `edit`, `previousTrainings`, `exercisesCount`, `setsCount`, `durationApprox`, `moreExercises`. Подзаголовок шторки собирается в коде как `exercisesCount · setsCount` (в макете у шторки времени нет, в отличие от сводки), повторы — как `'$sets × $reps'`.

### 10. Кнопка на борду 04

`Scaffold.body` становится `Column`: `Expanded(ListView(...))` + нижний блок `SafeArea(Padding(horizontal: 16, bottom: 16, child: FilledButton(height 48, radius 24, primary)))` с `pushNamed('/workout', arguments: training)`. Не `bottomNavigationBar` — так кнопка не перекрывает список и повторяет макет (кнопка на y=716, отступ 16).

## Risks / Trade-offs

- [Один и тот же набор данных живёт в JSON (`exerciseIds`) и в линк-таблице и может разойтись] → единственная точка записи — `ExerciseSetRepository.create()` в одной транзакции, порядок и состав берутся из сущности.
- [Подходы и повторы жёстко привязаны к упражнению] → одно движение с разными схемами = две записи справочника; принято осознанно, при необходимости переезд в линк-таблицу — отдельная правка сущностей.
- [Ссылка на удалённое упражнение или набор] → трактуется как «нет данных»: идентификатор пропускается (сценарий в spec `exercise-sets`), чистки сирот и каскадов не делаем.
- [База прежних сборок на устройстве больше не открывается] → принято: миграций нет, на устройстве приложение переустанавливается или очищаются данные приложения; относится и к уже установленной сборке с тренировками.
- [`update()` в этой итерации никем не вызывается и на устройстве не проверяется] → принято сознательно: это точка подключения будущей фичи выбора набора; API минимальный (обновление сущности целиком).
- [Состояния 09–12 нельзя увидеть на устройстве: демо-данных нет, а создания упражнений и наборов ещё нет] → следствие решения «не сеять данные»; проверяемы на живом приложении только борд 04 и состояние 13, остальные — по `flutter analyze` и последующему появлению набора.
- [Сгенерированный код (`*.g.dart`) в песочнице не перегенерировать] → Dart в песочнице нет, поэтому `.g.dart` правится вручную по детерминированному виду (для дефолтных полей json_serializable даёт `json['setId'] as String? ?? ''`), а пользователь прогоняет `dart run melos run codegen` и убеждается, что диффа нет.
- [Расхождение с макетом по мелочам (высоты, отступы)] → значения выписаны из бордов и перечислены в этом документе; спорит с ними только макет.
